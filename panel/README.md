# Мастер-панель (Marzban) — кастомный образ

Мастер собирается из патченного `gozargah/marzban` образа — три точечных
патча upstream-кода, все задокументированы прямо в `Dockerfile`. Раньше жили
только руками на сервере; теперь версионируются здесь.

## Деплой / пересборка на сервере
```bash
scp Dockerfile docker-compose.yml root@<панель>:/opt/marzban/
ssh root@<панель> 'cd /opt/marzban && docker compose build && docker compose up -d'
```
`.env` и `/var/lib/marzban` (БД, `xray_config.json`, TLS) на сервере не трогаем —
они не в этом репозитории и не должны там быть (креды, сертификаты).

## Патчи в Dockerfile
1. **sid-fix** — подписка отдавала `sid` от неверного объекта конфига.
2. **vless encryption=none** — явный параметр в ссылке для клиентов, которым он нужен.
3. **core_health_check try/except** — рестарт локального core мастера ничем не
   обёрнут в оригинале. Мастер по архитектуре не возит трафик (порт 443 занят
   панелью/CF) — его локальный xray физически не бинднется и падает на каждой
   проверке. Без try/except исключение раньше срывало весь health-check ДО
   цикла проверки **нод**. См. `../node/TROUBLESHOOTING.md`, раздел #3.

## Отдельно, не в образе (данные, не код)

`/var/lib/marzban/xray_config.json` на сервере — bind-mount, не часть образа.
Если там когда-то появится блок `"log": {"access": "...", "error": "..."}` с
путём вида `/var/lib/marzban-node/...` — это debug-хвост с прошлой сессии,
падает мастер (путь существует только у нод, не у мастера). Смотри
`../node/TROUBLESHOOTING.md`, раздел #3, там же команда для проверки причины
краша.

## Архитектура
Мастер — «мозг»: панель, БД, выдача клиентам подписок. Трафик не возит —
это делают ноды (см. `../node/`). Мастер тем не менее ВСЕГДА пытается поднять
тот же core-конфиг локально (ограничение апстрима Marzban, нет флага
«не поднимать инбаунды локально») — отсюда патч #3 выше, чтобы это не мешало
здоровью нод.
