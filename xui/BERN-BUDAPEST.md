# Вход Bern и выход Budapest

Схема проверена 21 ноября 2026, МСК. Адреса панелей, API-токены, ключи и персональные ссылки хранятся отдельно от репозитория. Bern и Budapest обозначают роли серверов.

## Рабочая схема

    Happ → Bern:443 (VLESS RAW + REALITY + Vision)
         → outbound hungary в Xray Bern
         → Budapest:443 (HAProxy → 3x-ui/Xray)
         → интернет с IP Budapest

На Bern правило 3x-ui совпадает по тегу входа in-443-tcp и email-метке клиента. Оно стоит после служебных правил и правил блокировки. Обычные клиенты используют прежние маршруты. При недоступном Budapest запрос назначенного клиента завершается ошибкой. Прямого резервного выхода через Bern для него нет.

На Budapest HAProxy принимает публичный TCP 443 и передаёт REALITY локальному Xray. Для HTTPS подписки у него есть отдельный backend на 2096. Файрвол принимает публичный TCP 443 только от Bern. Порты веб-панели и подписки закрыты снаружи. Администрирование идёт через SSH. Порт и путь панели проверяйте в действующей конфигурации.

Старый Marzban Budapest отвязан от бота. Его контейнер удалён, Docker отключён. Данные, старые скрипты, конфиги Nginx и Certbot, тестовые бэкапы и журналы перемещены в закрытый архив /root/hungary-retired.*. Действующий IP-сертификат расположен в /root/cert/ip/, его обслуживает cron acme.sh. TCP 80 оставлен для HTTP-01. Сертификат проверен, первое продление после очистки ещё не наблюдали.

На Bern отдельный сервис bern-hungary-pilot на TCP 54653 служил стендом и пока сохранён как запасной. Штатный маршрут на 443 управляется через 3x-ui. Снятые перед переносом снимки базы находятся на Bern в /var/backups/bern-hungary/. Для отмены маршрута одного клиента достаточно вернуть правило, полный снимок базы нужен при восстановлении панели.

## Как воспроизвести и проверить

1. Проверьте действующий профиль выхода Budapest и его HTTPS-трафик. Для исходящего VLESS используйте адрес, порт, SNI, публичный ключ, shortId и flow из одной актуальной ссылки.
2. По возможности сначала соберите отдельный тестовый Xray на Bern. У него один выход в Budapest и blackhole по умолчанию. Проверьте внешний IP через тестовый вход. Затем на изолированной копии замените адрес выхода на недоступный и убедитесь, что прямой выход через Bern не появляется.
3. Снимите согласованную копию SQLite и прочитайте текущий шаблон Xray из 3x-ui. Добавьте проверенный outbound и правило для отдельного клиента рабочего Bern:443. Сохраните через API и перезапустите Xray один раз. Сверьте живой конфиг и реальные запросы.
4. Проверьте два профиля. Для назначенного клиента внешний IP должен стать Budapest, для обычного клиента остаться прежним. Повторите после изменений файрвола с нового соединения. Так проверялся рабочий маршрут. Доступность из конкретной сети РФ проверяется только из неё.
5. Для нового клиента добавьте его точную email-метку в правило hungary. Убедитесь, что его вход включён в условие. Ссылка клиента Bern не меняется. Для отката уберите метку и снова примените правила. Отсутствие условия User у правила на общем входе направит туда всех клиентов этого входа.

## При повторном сбое

- Подписка, веб-панель и туннель проверяются отдельно. Пинг, HTTP 200 подписки и несколько килобайт в счётчике не доказывают, что через профиль грузится сайт. Проверяйте HTTPS-запрос, скачивание и IP выхода.
- Проверьте, по какому маршруту реально идёт тест. На Mac проба через уже активный VPN давала REALITY: received real certificate. Та же конфигурация через физический интерфейс прошла тест. Такой сбой сам по себе не доказывает фильтрацию ТСПУ.
- Сверьте слушатели Xray, 3x-ui и HAProxy с действующими портами. При переносе VLESS на другой порт HAProxy однажды остался направлять его на локальный 443, а подписка продолжала отвечать.
- Для RAW + REALITY + Vision используйте согласованный TLS target/SNI и профиль без HTTP-обёртки. У несовпадающей TCP-обёртки наблюдали EOF. Публичный ключ, shortId и UUID сверяйте локально, без вывода значений. Несколько разрешённых SNI в 3x-ui могут давать разные ссылки при обновлении. IP-сертификат нужен HTTPS по IP. Адрес подключения REALITY и его SNI задаются отдельно.
- Смена цели Google/GitHub, XHTTP/TLS и AmneziaWG дали отдельные успешные пробы, но не дали устойчивой работы в проблемной сети. AmneziaWG устанавливал рукопожатие и передавал килобайты. Для нашей схемы сработал стабильный вход Bern с выходом Budapest.
- Сверяйте конфигурацию после таймаута API, прежде чем повторять запись. Обновление Xray сохраняет весь шаблон. При нестабильном внешнем API успешным оказался SSH-туннель к панели с обычной TLS-проверкой имени. Используйте путь к SSH-ключу без чтения его содержимого.
- При правке UFW оставьте SSH и порт проверки сертификата, сохраните текущие правила и запланируйте автоматический откат. Отменяйте его после нового SSH-сеанса и сквозного теста. Устаревшие данные перемещайте из рабочих путей с возможностью восстановления.
- Временный access log включайте на согласованное окно и проверяйте отключение по живому конфигу. По отсутствию URL или IP в логе нельзя точно локализовать обрыв до Xray.

## Управление из Telegram

Именованные панели добавляются через XUI_MANAGED_PANELS, пример в .env.example. Откройте **Панели 3x-ui** или команду /xui, выберите панель, вход и клиента. Доступны состояние Xray, входы, исходящие, создание VLESS-клиента на выбранном входе по Telegram ID, ссылки, приостановка и возобновление доступа, продление, снятие ограничений, сброс трафика, удаление клиента с панели, выбор выхода и возврат к обычным маршрутам.

Для имеющейся цепочки Bern выбирайте outbound hungary. Для создания выхода из другой 3x-ui укажите для неё опциональный exit_client. Это email выделенного активного клиента с единственной ссылкой VLESS RAW/REALITY. Действие **Назначить выход → Через панель** читает профиль через API, добавляет исходящее и правило. Если одноимённый выход уже существует с другими данными, бот просит сверить настройки в 3x-ui. После сохранения бот проверяет правила и состояние Xray. Реальный IP выхода для новых конфигураций проверяется отдельно.

Для подключения закрытой панели Budapest организуйте постоянный защищённый канал с TLS-проверкой. Храните отдельные токены на хосте бота. Токены, ранее переданные в чате, замените.
